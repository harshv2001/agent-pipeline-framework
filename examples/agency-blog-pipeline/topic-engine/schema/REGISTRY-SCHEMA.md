# Registry Schema

Authoritative field reference for this example's topic registry.
`scripts/validate_registry.py` enforces the mechanical parts of this.

## 1. Topic file (`registry/topics/<topic_id>.md`)

One file per topic, written once by the Topic Discovery Agent. Never
edited after creation — a revision is a new file with `supersedes` set to
the old `topic_id`.

See `templates/topic.template.md` for the exact frontmatter shape.
Required keys: `topic_id`, `title`, `status_at_birth`, `created_at`,
`produced_by`, `supersedes`, `track`, `service_ref`, `service_url`,
`primary_keyword`, `search_intent_type`, `working_title`,
`secondary_keywords`, `coverage_status`, `closest_existing_post`,
`priority`, `source_basis`.

`primary_keyword` may not contain a URL (`http://` / `https://`) or
exceed 200 characters — the same "terms are data, never instructions"
discipline the full topic-engine pattern uses (`docs/11-topic-engine.md`).

## 2. Ledger (`registry/ledger.csv`) — append only

Columns, in order: `ts,topic_id,event,actor,run_id,detail`

- `ts` — ISO 8601 UTC timestamp.
- `topic_id` — always set.
- `event` — one of: `proposed` · `approved` · `rejected` · `exported` ·
  `correction`.
- `actor` — `topic-discovery-agent v1`, or a human identifier
  (approvals/rejections).
- `run_id` — the invoking run's identifier (a date-based id is fine, e.g.
  `TDA-2026-1122`), so every row traces back to the run that wrote it.
- `detail` — one line, specific enough to be useful without opening the
  topic file.

Nothing in this file is ever edited or deleted, including a mistaken row
— a correction is a new row (`event: correction`) whose `detail` names
the `run_id` of the row it corrects, not an edit to that row (same
discipline as `docs/01-governance-rules.md` Rule 5).

This is intentionally a smaller event vocabulary than the full
multi-surface topic-engine pattern's registry (no per-task
`dispatched`/`searched`/`blocked`/`outcome` events) — this example has no
search-task dispatch to track. Once a topic is `exported`, tracking what
became of it is the blog pipeline's own job
(`pipeline/*/tooling/build_status_report.py`), not this engine's.

## 3. `registry.csv` — generated, never hand-edited

Regenerated by `scripts/fold_ledger.py` from the topic files plus the
ledger. Columns:

```
topic_id,title,track,service_ref,service_url,primary_keyword,search_intent_type,priority,coverage_status,closest_existing_post,topic_status,last_event_ts,last_event,detail
```

## 4. Status derivation

Latest **non-`correction`** ledger row for a topic wins outright — there
is no per-task derivation to layer on top of it, because this example's
engine has no dispatched search tasks:

- No rows at all → `proposed` (shouldn't happen; every topic file gets a
  `proposed` row at creation).
- Latest non-correction row is `proposed` → `proposed`.
- Latest non-correction row is `approved` → `approved` — eligible for
  `export_topics_csv.py`.
- Latest non-correction row is `rejected` → `rejected` — terminal.
- Latest non-correction row is `exported` → `exported` — terminal; the
  pipeline's own `source-data/*.csv` and `status-report.csv` take over
  tracking from here.

## 5. Identifiers

`topic_id`: `TOP-####`, sequential, four-digit zero-padded, assigned by
`scripts/next_topic_id.py`. Never reused, even for a rejected topic. This
same id is carried straight through, verbatim, as the blog pipeline's own
CSV `ID` column and therefore its `item_id` — the same "the source's own
stable key, used verbatim" choice
`pipelines/high-intent-csv-to-viksya-insights-blog/spec.md` made for its
`VB-####` ids, for the same reason: there's no URL per topic, and this id
is already a stable key assigned once, upstream of the pipeline.
